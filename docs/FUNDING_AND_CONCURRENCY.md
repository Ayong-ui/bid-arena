# 资金与并发实现

> 业务规则与数值以 [`全栈评测-拍卖间-原文.md`](../全栈评测-拍卖间-原文.md) 为唯一依据。
> 本文件只写**怎么做、失败分支、必测边界**，不复述规则。若与原文冲突，以原文为准。

## 1. 数据结构与语义

- 钱包保存总额与冻结额两个整数列，另加并发控制所需列（版本号或由行锁承担）。
- **冻结不是转账**：它是用户同一钱包内的受限额度，不是资金离开钱包进入平台账户。因此不适用托管/escrow 语义。
- 流水是只追加的账目，每次冻结、释放、扣款都写入一行，并关联拍卖与 `requestId`，用于事后解释任意余额变化。

## 2. 差额冻结算法

一次出价落到某金额时，用户在本场需要新增的冻结为：

```
add = max(0, amount - already_frozen_in_this_auction)
```

- `already_frozen_in_this_auction` 是该用户**当前**在本场的冻结额（被超越释放后归零，再次出价需重新全额冻结）。
- 成为新领先者时，先释放上一领先者在本场的全部冻结，再冻结新领先者的差额。
- 校验与写入必须同事务，且先校验可用余额再落库，避免"价格已更新、资金未冻结"或反向的半完成状态。

## 3. 锁顺序与死锁

固定顺序，全部入口一致：

```
auction 行  →  wallet 行（按 user_id 升序）  →  bid_request / bids
```

- **禁止**先锁钱包再锁拍卖。
- 并发涉及多个钱包时按 `user_id` 升序加锁，消除交叉死锁。
- 死锁或锁等待超时按有限次数重试（带退避），超过上限返回可识别的冲突错误。
- `(auction_id, user_id, request_id)` 唯一约束是并发正确性的最后兜底，不依赖应用层"先查再判"。

## 4. 幂等记录生命周期

```
insert PENDING (唯一键)
  → 处理
  → update DONE + 首次业务结果快照
     （失败则记录结果码，仍占位，保证重试不重复生效）
```

- 重试命中 `DONE`：返回**首次**业务结果，不新增价格、冻结、流水或 `seq`。
- 重试命中 `PENDING`：说明首次仍在处理中，返回冲突类错误（见 `openapi.yaml` 错误码）。
- 请求头幂等键与请求体 `requestId` 必须一致，不一致按参数错误处理。
- `requestId` 按用户隔离，并校验长度与格式。

## 5. 结算与取消

### 结算

1. 扫描器找到**到期且仍为 `RUNNING`** 的拍卖。这一步不锁定任何行，只产生候选集：两个实例会得到相同的候选集，这是允许的。
2. 每场单独开一个事务，第一步就是锁拍卖行——**同一场拍卖的结算与取消、结算与出价，全部串行化在这一把锁上**。
3. 锁内读 `settlements`：已存在则直接返回已有结论（见下文“重放的适用范围”），不重复扣款、不重复记流水。
4. 未过期不结（直接报错，不写任何痕迹）；已过期则按有无领先者定原因：有赢家 → `TIMEOUT`，无出价 → `NO_BIDS`。
5. 锁定本场全部按场冻结与相关钱包（按 `user_id` 升序），赢家冻结转扣款，其余冻结释放。**赢家冻结额与成交价不等就报错断事务**，而不是跳过——赢家冻结为 0 却仍然成交，等于东西拿走了钱没付，而这种缺陷在对账上看起来完全是平的。
6. 写唯一成交记录、置终态，提交。

**没有"抢占结算态"这一步。** `SETTLING` 写在结算事务内部、不单独提交，外部观测不到。把"已抢占但钱还没动"做成持久状态的代价是：进程崩溃会留下一个资金悬空、且扫描"到期 `RUNNING`"再也找不到的死状态，必须再写一套超时回收。单事务没有这个中间态，崩溃等于什么都没发生，下一轮扫描自然重试。

### 重复触发如何收敛

| 层 | 作用 | 去掉它会怎样 |
|---|---|---|
| 拍卖行锁 | 让重复触发**串行**，后到者看得到先到者的提交 | 两个事务同时动同一笔钱 |
| 锁内读 `settlements` | 让重复触发返回**同一结论** | 第二次撞主键，变成一个报错 |
| `settlements` 主键 | 兼底，任何路径都写不进第二条 | 理论上重复扣款 |

### 重放的适用范围

只有"**同一种结束方式**已经发生过"才算重放。取消打到已成交的拍卖上返回 `INVALID_STATE`，而不是重放那个 `TIMEOUT` 结果——后者等于告诉调用方"你的取消已生效"，而实际发生的是成交，这是在对调用方说谎。

### 单场失败不阻塞整批

某一场因数据异常结不了（例如冻结额与价格不一致），只记 ERROR 并留下重试，不中断同一轮里其他到期拍卖。否则一场脏数据会把后面所有拍卖一起拖住。

### 取消

- 只允许在草稿态或进行态取消；已结束的拍卖拒绝。
- 终态是 `CANCELLED`（不是 `FINISHED`），与原文状态机一致；成交记录 reason 为 `CANCELLED`，成交价为 0。
- 取消在一个事务内释放本场全部冻结、写流水、改状态并广播。
- 取消与结算互斥：两者都先要拍卖行锁，谁先拿到谁定结局。

## 6. 失败分支

| 失败点 | 表现 | 处理 |
|---|---|---|
| 校验不通过（状态/时间/关系/价格/余额） | 无任何资金与价格变化 | 返回业务错误，不写业务数据 |
| 幂等命中已完成 | 无新变化 | 返回首次结果，标记幂等 |
| 幂等命中处理中 | 无新变化 | 返回冲突 |
| 锁等待/死锁 | 事务回滚 | 有限重试 |
| 事务中途异常 | 全部回滚 | 重试或返回未知错误 |
| 事务已提交、广播失败 | 数据库已生效 | **不回滚**，记日志，靠快照恢复 |
| 结算重复触发 | 已有成交记录 | 安全返回，不重复扣款 |
| 结算时赢家冻结额与成交价不一致 | 无任何资金变化 | 报错并保留在 `RUNNING` 下轮重试，**不放行** |
| 一场结算失败 | 其他场次不受影响 | 单场记 ERROR，同轮继续结算其余拍卖 |

## 7. 必测边界

- 拒绝类：非法状态、未加入、低于最低加价、服务端已截止、余额不足——资金与价格均不变。
- 冻结类：同一用户连续加价只增加差额；换庄时旧领先者全额释放。
- 并发类：两用户并发出价后，领先者、价格、冻结、流水可由数据库唯一解释。
- 结算类：到期/取消/重复触发/重启恢复只产生一条成交结果；无出价不扣款；结算后本场冻结归零。
- 取消类：`DRAFT`/`RUNNING` 可取消且全部释放；已结束的拍卖取消被拒。
- 原子类：任一失败步骤不得留下半完成状态。
